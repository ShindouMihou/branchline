## Git and GitHub approvals

Run read-only Git/GitHub queries, builds, tests, and safe local-only changes directly. This includes fetch without force/pruning, staging/unstaging without moving HEAD or discarding files, stash save/apply/pop with normal conflict protections, and local branch creation/rename/switching that preserves existing work. Disposable isolated test fixtures may also create commits, rewrite history, and push to local fixture remotes; they must not use real credentials or remote services, or affect user repositories or shared resources.

Before commits in real repositories, pushes/remote writes, pull-request or GitHub changes, history rewrites, deletion, or operations that can discard/overwrite work, load `branchline-git-approval` at `{{skill_path}}` and use the connected Branchline MCP server. Authentication/security changes and changes to publication destinations also require review. Classify scripts and aliases by their effects. If any action in a chain needs approval, submit the whole unchanged chain. Inspect uncertainty first; use Branchline if safe local effects cannot be established. Preserve stricter explicit user or repository requirements.

For gated actions, use `branchline_propose_command`, request native review, and wait with `branchline_wait_for_result`. Continue waiting after a timeout; timeout is not approval. Report the actual result and only verified pull request URLs. Task authorization does not replace native approval for these actions. If Branchline is unavailable, pause gated actions and tell the user; safe direct work can continue.
